PERFORMANCE & ALGORITHMIC IMPROVEMENTS: SEARCH, FILTER, AND PAGINATION
========================================================================
1. WHAT WAS CHECKED & DETECTED ISSUES
-------------------------------------
* Frontend-Only Filtering: 
  Previously, the frontend dispatches 'fetchWines()' and 'fetchInventories()' on mount to fetch *all* wines and *all* inventory entries in the database, loading them into the client browser's memory.
* High Algorithmic Complexity: 
  The frontend then filtered these lists using client-side JavaScript array.filter. For a database of size N wines and M inventories:
  - Space Complexity: O(N + M) memory on the browser.
  - Time Complexity: O(N * M) or O(N + M) CPU cycles for each filter change/render lookup.
  - Network overhead: Down-streaming the entire database of wines and inventories on every page load.
* Lack of Database Indexing:
  The database field 'wine_type' (which is the primary filter criteria) did not have a database index. As the database grows on AWS, any query filtering by wine type would perform a slow sequential table scan instead of an index scan.
* Lack of Pagination:
  The API loaded all records in a single payload. If the database grows to thousands of wines, the payload size increases linearly, causing high latency, memory pressure, and API timeouts.
* Global Loading on Detail Pages:
  Detail pages ('InventoryList.jsx' and 'AddInventory.jsx') were loading the entire global wines list into memory and calling 'wines.find()' just to display a single wine's attributes.
2. ALGORITHMIC AND DATA STRUCTURE IMPROVEMENTS
----------------------------------------------
We moved the searching, filtering, and pagination logic from client-side memory to the PostgreSQL database on the backend:
* Backend Pagination (O(1) Page Size):
  We introduced 'WinePagination' with a page size of 10. The backend now uses SQL LIMIT and OFFSET. The browser only loads 10 records at a time, making page load times independent of database size:
  - Space Complexity: O(1) page size in browser memory.
  - Time Complexity: O(1) filter/render lookup.
* Database Indexing (O(log N) Lookup):
  We added 'db_index=True' to 'wine_type' in 'Wine' model (migration '0012_alter_wine_wine_type' was generated and applied). Filtering by wine type now performs a fast index scan instead of scanning every row.
* Backend Filtering:
  The 'WineViewSet.get_queryset()' was customized to accept query parameters:
  - 'restaurant_id': Filters wines associated with the restaurant via joining the 'Inventory' junction table in the DB.
  - 'wine_type': Filters matching wine types at the database level.
* Serializer Optimization:
  We exposed the 'wine_type' field as a read-only field directly in 'InventorySerializer'. This allowed the public QR code menu view ('WineListMenu.jsx') to completely eliminate its dependency on 'fetchWines()' and fetch only inventories, reducing data overhead.
* Single Fetch by ID:
  We added the 'fetchWineById' action in Redux, and refactored 'InventoryList.jsx' and 'AddInventory.jsx' to retrieve only the specific wine record from '/api/wines/wines/{id}/' upon loading.

### Proving Query Optimization with Query Tracing:
During test runs, we verified the queries generated by the ORM. The paginated search and filter request translates into:
1. `SELECT COUNT(*) AS "__count" FROM "wines_wine"` (to compute total pages for pagination metadata).
2. `SELECT ... FROM "wines_wine" WHERE wine_type = 'red' ORDER BY id LIMIT 10` (fast indexed scan returning only 10 rows).
3. `SELECT ... FROM "wines_grape" WHERE wine_id IN (...)` (prefetches grapes for the 10 selected wines in a single query).
This reduces the total query count from O(N) database operations down to a constant 3 database operations, drastically improving latency and database resource consumption.
